# ANDROID_BUGS.md

Bugs found while porting the import, gesture, storage and project-layout subsystems, in the state
they were found. "Fixed" means the fix is in this branch with a test that failed without it.

## Fixed in this branch

| # | Symptom | Cause | Fix | Test |
| --- | --- | --- | --- | --- |
| 1 | Every WAV and WebP picked on a phone classified as `Unknown` | my `riffForm` compared the form type at byte 10 instead of byte 8 (`"RIFF" + 4-byte size + "WAVE"`) | read `subspan(8)` | `AndroidAssetImport.MagicBeatsExtension` |
| 2 | A dotfile's name was treated as an extension (`.bashrc` → type of `bashrc`) | the dot was searched without checking something precedes it | `dot <= nameStart` is not an extension | `AndroidAssetImport.ExtensionDecidesWhenBytesSayNothing` |
| 3 | An extension-less Ogg import was saved as `clip.wav` | the audio fallback was a constant `"wav"` | `audioExtensionFor(kindFromMagic(bytes))` | `AndroidAssetImport.ImportedAssetNameIsAnAssetName` |
| 4 | A provider's name with an embedded NUL produced `abc.tx` instead of `abc.txt` | the control byte was dropped *after* the cut was measured | the cut is measured on surviving bytes | `AndroidAssetImport.SanitizeKeepsUnicodeAndDropsControls` |
| 5 | `AndroidStorageSpace.h` did not compile alone | `<cstddef>` missing (`size_t`) | include added | each header compiled by itself |
| 6a | `.webp` is an editor Texture extension but **no decoder in the tree reads WebP** (stb_image has none; grep `stbi__webp` is empty), so a phone photo shared as WebP is accepted, named, and fails only at decode | `editor/asset/AssetTypes.cpp` lists `.webp`; `engine/libs/stb/stb_image.h` has no WebP code | reported by the import now (`decodeSupportOf` → NeedsConversion/PNG); the real fix is a WebP decoder (libwebp) or removing the extension — main agent's call |
| 6b | HEIC/AVIF (an iPhone's photo) and M4A/AAC were `Unknown` to every check: all ISO-BMFF files begin with `ftyp` at byte 4 and nothing looked | `kindFromMagic` had no ISO-BMFF branch | `ImportKind::IsoBmff`, and the support checks send it to `BitmapFactory`/`MediaCodec` | `AndroidAssetImport.WebP*`, `.TheFormats*` |
| 6c | A portrait phone photo imports sideways with its width and height swapped: the engine reads no EXIF orientation anywhere, and `TextureData` has no rotate | `grep -ri exif engine/core/texture` empty; `TextureData.h:149` has `flipVertical` only | `AndroidImageOrientation.h` parses and maps the tag (the *policy* is fixed; the import still has to call it and apply the transform, bug 10c) |
| 6 | A 120 MP camera photo would be decoded as 432 MB of RGBA before any check | nothing reads an image's dimensions before the decoder allocates | `AndroidImageLimits.h`: header-only size, then downscale/refuse (this fixes the *policy*; the decode path still has to call it, bug 10) | `AndroidImageLimits.*` (6 cases) |

## Found, not fixed (belongs to another owner or needs a device)

| # | Finding | Evidence | Owner |
| --- | --- | --- | --- |
| 6 | A save on a full phone is refused only when the write fails: no free-space check precedes it, so a 2 GB capture can fill the volume and take every later save with it | `FileUtils.cpp:80` maps ENOSPC but nothing asks first; no `statvfs` in the tree | platform seam (`System.h`) — proposal in `ANDROID_HANDOFF.md` |
| 7 | The player's `data://` is app-private: uninstalling the app deletes every save, and no file manager can reach it without adb | `JasperEngineAndroid.cpp:218` returns `internalDataPath` | product decision; `accessFor(AppPrivate)` now states the warning |
| 8 | A project on a SAF grant cannot be saved atomically: a provider replaces a file by copying over it | Android's `DocumentsContract` has no rename-over; `io::writeFileAtomic` assumes rename | editor's Android backend (main agent) |
| 10b | `Data::seek` clamps against `dataLength - 1` on an unsigned length: on a file of 0 bytes (or any seek past the end of a short one) the subtraction underflows, the clamp does nothing, and `Data::read` `memcpy`s from `dataPtr + offset` with a huge offset. Reachable from Lua: `FileData.newFile(false)` → `seek(-4)` → `read8()` **SEGVs** (reproduced under ASan/UBSan, `/tmp/datarepro2.cpp`). `Data.cpp` is the main agent's core file, so this is documented with the patch rather than edited; `ANDROID_HANDOFF.md` §4 has it | ASan SEGV at `engine/core/io/Data.cpp:59` | main agent (`engine/core/io/Data.cpp`) |
| 10g | `.m4a` / `.aac` / `.opus` were `AssetType::Unknown` ("copied as it is") instead of Audio, and `.webp` / `.heic` / `.avif` only by magic: `playbackSupportOf` and `decodeSupportOf` were unreachable for exactly the phone formats they were written for, so the report could never say "will not play" | found by running `tools/android-asset-report.py` on a real folder | fixed: the extension tables include them, with a test |
| 10e | A .gltf imported alone on a phone loads with missing geometry and missing textures, and the engine **suppresses** the warnings (the "File not found"/"Failed to load external 'uri'" lines are filtered for a cooked model), so the user is told nothing | `MeshSystem.cpp:455-482` filters them, `:2116` resolves URIs against the .gltf's directory | policy fixed: `AndroidModelSidecars.h` names the files to bring and the preflight reports them (bug 10f is the wiring) |
| 10f | `gltfSidecars` is not wired into the import UI, so `missingSidecars` is computed and not shown | this branch has no editor call site (the editor is the main agent's) | proposed: the Project panel's drop handler asks `preflightImports` and offers "bring these N files too" |
| 10d | An `#endif` that closed the guard before the last block: `AndroidImageLimits.h` put `decodeSupportOf` after it, so a second include redefined `ImageSupport`/`ImageSupportAnswer` (`multiple definition`, caught only when `AndroidImportPreflight.h` included it from a second place) | found while writing the preflight | fixed: the guard closes at the end of the file, and the suite includes four headers twice on purpose |
| 10c | `AndroidImageOrientation` is not wired into the import, and applying it needs a rotate the engine does not have (`TextureData::flipVertical` only). On Android the cheapest route is `BitmapFactory.decodeStream` with a `Matrix` (rotate/flip) and `inSampleSize`, which also solves bug 10's 432 MB peak — one decode that the platform does at the right size and orientation | the policy is tested, the decode path is unchanged | runtime import path (status §5.3b/5.4) |
| 10 | `AndroidImageLimits` is not wired into the decode: the importer must read the first 64 KiB and honour the verdict, and stb_image cannot decode at a reduced scale, so the peak allocation is only avoided through JPEG `inSampleSize` (Android `BitmapFactory`) or a vendored libjpeg-turbo | the policy is tested, the decode path is unchanged | runtime import path (see status §5.4) |
| 9 | Nothing computes a pinch today: a game on a phone gets per-finger data only | `grep -i pinch engine/core` empty | fixed for the derived layer here; the Android editor's backend still has to use it |
